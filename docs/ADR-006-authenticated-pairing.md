# ADR-006: Authenticated device pairing

Status: M1 candidate

## Goal

Pairing must establish which device identity public keys belong to the two participants before those keys are trusted to authorize private-session creation or participant-originated lifecycle requests. Relay delivery alone is not identity proof.

## Device identity key

Each Android installation owns a stable signing key generated by the `AndroidKeyStore` provider. The M1 baseline uses NIST P-256 (`secp256r1`) with `SHA256withECDSA`, and the private key is authorized for signing only. The private key is never serialized into the pairing protocol.

StrongBox is an optional capability upgrade, not a compatibility requirement. Production code must record/report the actual Android Keystore security level where available and must not claim hardware protection when the key is software-backed.

Changing or losing the device identity key changes the device identity. Existing peer trust must not silently migrate to a replacement key.

## Canonical transcript

The final pairing transcript binds, at minimum:

- protocol version and domain separator
- random one-time `pairingId`
- creation and expiry timestamps
- inviter device ID, immutable identity public-key SPKI bytes, and immutable 32-byte nonce
- invitee device ID, immutable identity public-key SPKI bytes, and immutable 32-byte nonce
- explicit inviter/invitee roles in each signature payload

Canonical encoding is length-prefixed binary data, not implementation-dependent JSON serialization. Binary inputs are defensively copied at the transcript boundary so caller mutation cannot change already-reviewed signing state. Both peers sign the same transcript with role-separated signature payloads. Peer/key substitution, field modification, malformed peer key material, or role reflection must fail closed.

## Human authentication requirement

Cryptographic self-signatures prove possession of the included private keys; they do not by themselves prove that those keys belong to the intended human peer. A relationship MUST NOT enter `VERIFIED` until the users complete an out-of-band verification step derived from the final transcript.

The primary in-person flow should use a final QR verification. A remote safety-code format may be added, but its encoding and usability must be separately reviewed before it becomes an accepted authentication path. The M1 identity/transcript probe does not satisfy this human-verification gate by itself.

## Handshake target

1. Inviter creates an expiring one-time invite containing its device identity public key and fresh nonce.
2. Invitee contributes its identity public key and fresh nonce and signs the final transcript as `invitee`.
3. Inviter verifies the invitee signature, signs the same transcript as `inviter`, and returns confirmation.
4. Both devices verify both signatures and derive the same transcript digest.
5. Users complete the out-of-band verification step.
6. Only then is the relationship persisted as `VERIFIED`.

A consumed or expired `pairingId` must not be reusable. A key change returns the relationship to an unverified/key-changed state and requires explicit re-verification.

## Lifecycle signer boundary

Participant identity keys authenticate participant-originated requests such as session creation and revoke initiation. The authoritative service state/lease signer is a separate trust boundary and must be explicitly specified; a relay does not gain signing authority merely by carrying protocol messages.

This ADR does not yet accept a service signing-key distribution/rotation design, remote safety-code UX, or backend replay-consumption implementation. Those remain pairing gates.
